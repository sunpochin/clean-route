# 程式碼慣例 / Code Conventions

## 1. 檔案開頭導覽

新建或修改可寫註解的人工維護檔案時，若開頭沒有導覽，必須補上一段繁體中文說明，交代三件事：

- **檔案用途**：這個檔案做什麼。
- **所在層**：它在哪一層、扮演什麼角色（例如「src/domain；純函式」）。
- **主要關聯**：主要被誰使用、依賴誰、相關文件。

格式依語言使用合法註解：TS／JS 用 `//`、CSS 用 `/* */`、Markdown 用 `<!-- -->`。有 `"use client"` 的檔案，指令必須在第一行，導覽放在它之後。JSON、lockfile、產生檔、第三方檔不硬塞註解。

## 2. 註解寫「為什麼」

- 不要翻譯程式碼（「迴圈跑過每個點」）。要寫的是：為什麼選這個值、為什麼不用直覺的寫法、踩過什麼坑、執行順序為什麼重要。
- 魔術數字一律具名常數，並註明來源（實測值、上游限制、UX 理由）。

## 3. 畫面狀態區分（AGENTS.md § 3.4 的落地方式）

任何會抓資料的畫面至少區分四種狀態，而且文案不同：

| 狀態 | 例子 |
| --- | --- |
| 載入中 | 「正在查詢附近清運點…」 |
| 失敗 | 「資料抓取失敗…這不代表附近沒有垃圾車」＋重試按鈕 |
| 成功但為空 | 「方圓 600 公尺內沒有新北市的清運點」 |
| 成功 | 列表 |

- 讀取失敗與表單送出失敗（未來的推播設定等）不得共用同一個 state 變數。
- 輪詢資料（即時車輛）更新失敗時，保留最後一次資料並顯示警示條，而非清空；每筆資料的時間戳要顯示出來。

## 4. 元件與檔案大小

- 頁面只負責組合；可獨立的視覺區塊寫成 `src/components` 元件，資料狀態寫成 `src/hooks`。
- 單檔原則上 ≤ 300 行；超過 400 行評估拆分；拆分依職責，不做 `part1`／`helpers2` 這種無語意切割。
- 與任務無關的重構另開 issue，不要順手做。

## 5. 可及性

- 狀態不得只靠顏色：收運種類用文字標籤、過期位置同時有文字與 aria-label。
- 動畫尊重 `prefers-reduced-motion`（Tailwind `motion-reduce:`、地圖 `duration: 0`）。
- 觸控目標至少 40–48 px（`btn-*` class 已內建）。
